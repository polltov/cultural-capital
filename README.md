# Культурная Столица

Сайт экскурсионного проекта «Культурная Столица» (экскурсии по Петербургу для детей и взрослых) с админ-панелью: каталог экскурсий и сеансов, онлайн-продажа билетов с оплатой через ЮKassa (с уведомлением об оплаченных заказах в Telegram), новости, список участников сеанса с печатью и выгрузкой в CSV, отметка прихода по QR-коду билета.

Стек: Next.js 16 (App Router), TypeScript, Drizzle ORM + стандартный Postgres, объектное хранилище S3 (обложки), ЮKassa (онлайн-оплата), письма по SMTP (nodemailer), Vitest. Сайт работает в России: сервер, база и хранилище — в Селектеле, сайт — в Docker за Caddy (HTTPS), выкладка — через GitHub Actions (раздел «Где работает сайт»).

## Публичный сайт

| Адрес | Что там |
| --- | --- |
| `/` | первый экран с ближайшей экскурсией, каталог, ближайшие даты, «О нас», как проходит экскурсия, отзывы, индивидуальные экскурсии, новости, вопросы |
| `/tours/<адрес>` | страница экскурсии: описание, маршрут, место встречи, что взять, условия, выбор даты и покупка, другие экскурсии |
| `/afisha` | все будущие сеансы по месяцам с покупкой в один клик |
| `/news`, `/news/<адрес>` | новости |
| `/order/<токен>` | билет после оплаты (по секретной ссылке, не индексируется, без Метрики) |
| `/account` | личный кабинет покупателя «Мои билеты»: вход по одноразовой ссылке на почту, все заказы на этот email (не индексируется) |
| `/offer`, `/privacy`, `/consent` | документы |

Всё про экскурсии (тексты, фото, цены, даты, место встречи и «что взять с собой») редактируется в админке; главная, афиша и страницы экскурсий обновляются сразу после сохранения и после каждой покупки. Для поисковиков есть `sitemap.xml`, `robots.txt` и микроразметка schema.org (экскурсии и их сеансы, организация, хлебные крошки). Ссылка на экскурсию в Telegram и ВКонтакте показывает собственную картинку-превью: название, подзаголовок, маршрут и обложка экскурсии в фирменном стиле (`src/app/(site)/tours/[slug]/opengraph-image.tsx`, шрифты и логотип для неё — в `src/assets/og/`).

- **Админка → Сайт.** Владелец, администраторы и редакторы могут менять тексты и две фотографии первого экрана, пункты «Почему с нами интересно», шаги «Как проходит экскурсия», отзывы, блок индивидуальных экскурсий, описание в подвале и SEO главной. Блоки публикуются по отдельности.
- **Контакты.** Telegram, WhatsApp, ВКонтакте, публичные телефон и почта редактируются в «Сайт → Контакты». Если телефон или почта пустые, сайт подставляет значения из реквизитов. Эти поля не меняют реквизиты в юридических документах и настройки отправки билетов.
- **Обложки экскурсий.** Фото загружается в админке; на сайт оно уходит уменьшенной копией под экран. Лучше горизонтальное фото от 1600 px по ширине. Пока фото нет, вместо него — фирменная гравюра с атлантами на цветной подложке.
- **Логотип.** `public/brand/` — векторные копии логотипа (знак, надпись, орнамент «•—✳—•»), иконка для iOS и картинка для превью ссылок `og.jpg` (1200×630); исходники — PNG в `public/assets/`. Иконка вкладки (`favicon.svg`, PNG 32 и 120 px, `public/favicon.ico`) — упрощённый портал с логотипа на терракоте: гравюра в 16 px не читается; подключается в `src/lib/site-icons.ts`.
- **Шрифты.** Лежат в `public/fonts/` и подключаются в `src/app/fonts.css` (Prata — заголовки, Playfair Display — курсивные акценты, PT Serif — текст, PT Sans — интерфейс; все под SIL Open Font License). Там же — запасные системные шрифты, подогнанные по ширине, чтобы страница не «прыгала» при загрузке. Цифры в заголовочном шрифте взяты из Playfair Display (у Prata единица неотличима от «l»): файл `prata-digits-*.woff2` и цифры в `src/assets/og/Prata-Regular.ttf` собирает `python scripts/fonts/prata-digits.py` (нужны `fonttools` и `brotli`).
- **Анимации.** Переходы между страницами — `src/components/site/transitions.tsx` (React `<ViewTransition>`): из каталога обложка карточки перетекает в обложку страницы экскурсии, переходы «вглубь» и «назад» сдвигают страницу, шапка стоит на месте. Движение на странице (появление при прокрутке, вход первого экрана, раскрытие вопросов) — CSS в `site.css`, раздел 26. Всё отключается системной настройкой «уменьшить движение»; браузеры без поддержки просто показывают страницы без анимации.

## Личный кабинет покупателя

«Мои билеты» (`/account`, ссылка в шапке, меню и подвале, а также в письме с билетом): покупатель вводит email, на который покупал, и получает одноразовую ссылку для входа (30 минут). Ссылка открывает страницу с кнопкой «Войти» — сам переход по ссылке её не тратит, так что почтовые проверки ссылок вход не ломают. После входа cookie действует 30 дней. В кабинете — оплаченные, прошедшие и отменённые заказы на этот адрес (без учёта регистра) со ссылками на билеты. Ответ на запрос ссылки одинаковый, есть заказы или нет; лимит — 3 запроса на адрес и 5 с IP в час. Нужны настроенная почта (SMTP, раздел «Почта») и `SESSION_SECRET`.

## Отметка прихода по QR-коду

На билете (страница заказа, печать, письма с билетом и напоминанием) есть QR-код. Он ведёт на `/admin/checkin/<токен заказа>`: гид сканирует его обычной камерой телефона, на котором вошёл в админку, видит, чей это билет, на какой сеанс и сколько человек, и нажимает «Отметить приход». Если гид ещё не вошёл, после входа его вернёт на эту же страницу. Отметки видны и ставятся вручную в списке участников сеанса (колонка «Пришли»), попадают в CSV. QR-код показывается только у оплаченного заказа; у отменённого картинка в старом письме пропадает.

## Аналитика

**Источник заказа.** Когда человек приходит на сайт по ссылке с UTM-метками или с другого сайта, браузер на 30 дней запоминает источник в cookie `kc_src` (прямой заход по закладке источник не затирает), а при покупке он записывается в заказ (`src/lib/attribution.ts`). Источник виден в карточке заказа, сводка — в админке, раздел «Источники» (`/admin/sources`, ссылка есть и на «Сводке»): сколько покупок начато и оплачено, билетов и сумма за 7, 30 или 90 дней по каждому источнику, каналу и кампании. Персональных данных в сводке нет.

Ссылки в рекламе, постах и у партнёров размечаются так (латиницей, без пробелов):

| Метка | Что писать | Примеры |
| --- | --- | --- |
| `utm_source` | площадка или партнёр | `vk`, `telegram`, `yandex`, `kudago`, `hotel-nevsky` |
| `utm_medium` | тип размещения | `cpc` (платная реклама), `post` (посев, пост), `partner`, `email` |
| `utm_campaign` | кампания | `zima-2027`, `egypt-hall` |
| `utm_content` | вариант объявления, необязательно | `video-1` |

Пример: `https://culturaltours.ru/tours/<адрес>?utm_source=vk&utm_medium=cpc&utm_campaign=zima-2027`. Яндекс Директ с автоматической разметкой добавляет к ссылке только `yclid` — такой заход записывается как `yandex / cpc`. Без меток источник — домен сайта, с которого перешли (`yandex.ru / organic`, `vk.com / social`, `kudago.com / referral`).

**Яндекс Метрика** подключена в коде, но выключена, пока не задан номер счётчика. Работает только после согласия посетителя (плашка «Разрешить / Отказаться» внизу страницы; изменить решение можно в политике, раздел 7), не загружается на страницах билета `/order/…` и входа в кабинет `/account/…`, карта кликов и Вебвизор выключены. Чтобы включить:

1. В [Метрике](https://metrika.yandex.ru) от аккаунта Яндекса компании: «Добавить счётчик», адрес `culturaltours.ru`, Вебвизор не включать.
2. Номер счётчика записать в `METRIKA_ID` в `src/lib/analytics.ts` и выложить сайт.
3. В настройках счётчика → «Цели» создать три цели типа «JavaScript-событие» с идентификаторами:
   - `checkout_open` — открыл окно покупки билета;
   - `checkout_pay` — заполнил данные и дошёл до оплаты (с суммой заказа: в отчётах виден доход по цели);
   - `contact_click` — нажал на Telegram, WhatsApp, ВКонтакте, телефон или почту (канал в параметре `channel`).

Оплату Метрика не видит: страница билета с секретной ссылкой в неё не отправляется. Оплаченные заказы по источникам — в админке, раздел «Источники».

## Локальная разработка

1. Поднять Postgres:

   ```bash
   docker compose -f docker-compose.test.yml up -d
   ```

   Контейнер слушает порт 54329; базы `dev` (для `npm run dev`) и `test` (для интеграционных тестов).

2. Создать `.env.local` из шаблона и заполнить значения:

   ```bash
   cp .env.example .env.local
   ```

   Важно: Next раскрывает `$VAR` в `.env`-файлах, поэтому в `.env.local` каждый `$` в `ADMIN_PASSWORD_HASH` нужно экранировать как `\$` (кавычки не помогают), например `\$2b\$12\$...`.

3. Применить миграции и заполнить базу начальными данными:

   ```bash
   npm install
   npm run db:migrate
   npm run db:seed
   npm run dev
   ```

   Сайт: http://localhost:3000, админка: http://localhost:3000/admin.

## Онлайн-оплата

Билет покупается на сайте: оплата через ЮKassa (виджет на странице), билет и кассовый чек приходят на email. Запросы к ЮKassa, Telegram и хранилищу S3 идут напрямую через `fetch`, без SDK; письма уходят по SMTP.

- **Тестовый магазин.** Для разработки задайте `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` **тестового** магазина ЮKassa (тестовые карты и тестовый СБП). Боевые ключи ставятся в `app.env` на сервере, когда сайт уже открывается по своему домену и письма уходят.
- **Уведомления ЮKassa.** В кабинете ЮKassa укажите URL уведомлений `https://<домен>/api/payments/yookassa` и включите события `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
- **Отмена части билетов.** В карточке оплаченного заказа «Отменить часть билетов»: сколько детских и взрослых отменить и сумма возврата (по правилу 24 ч / 50% от стоимости этих билетов, редактируется). Места освобождаются сразу, остальные билеты действуют, клиенту уходит письмо. Возвратов по заказу может быть несколько; сумма заказа остаётся суммой платежа, возвращённое копится, история видна в карточке. «Отменить и вернуть» после частичных отмен предлагает не больше невозвращённого остатка. При `RECEIPT_CLOSING=on` закрывающий чек по заказу с частичной отменой автоматически не выбивается (сумма остатка не равна стоимости оставшихся билетов) — придёт тревога, чек оформляется в кабинете ЮKassa.
- **Возврат в кабинете ЮKassa.** Если «Отменить и вернуть» в админке не проходит, оформите возврат в кабинете ЮKassa. Сайт сам увидит его — по уведомлению `refund.succeeded`, при повторном нажатии «Отменить и вернуть» или ночью перед закрывающим чеком — и отменит заказ с фактически возвращённой суммой; второго возврата не будет.
- **Ночная задача.** Контейнер `cron` на сервере вызывает `/api/cron/nightly` раз в сутки в 00:00 UTC (03:00 по Москве); расписание лежит в `deploy/cron.mjs`. Запрос защищён `CRON_SECRET`: расписание передаёт его заголовком `Authorization: Bearer <секрет>`, без секрета роут отвечает 401. Задача подбирает оплаты, чьи уведомления потерялись, переводит просроченные заказы в `expired`, а прошедшие экскурсии — в `done` (и при `RECEIPT_CLOSING=on` выбивает закрывающие чеки). Если что-то по заказам не удалось, в Telegram приходит тревога с числом ошибок (подробности — в журнале сайта: `docker compose logs app`). Вручную на сервере, в `~/app`: `docker compose run --rm cron node cron.mjs /api/cron/nightly`.
- **Дневная задача.** `/api/cron/daily` — раз в сутки в 15:00 UTC (18:00 по Москве), защищена тем же `CRON_SECRET`. Шлёт напоминание об экскурсии всем оплаченным заказам на сеансы до конца завтрашнего дня (кроме купивших меньше 6 часов назад; после переноса на другой сеанс напоминание уйдёт заново). При `ABANDONED_MAIL=on` ещё шлёт «вы не завершили оплату» по неоплаченным заказам за последние 3 дня, если на ту же дату хватает мест, экскурсия не раньше чем через 3 часа, а покупатель после этого не оформлял новых заказов; одному адресу — не чаще раза в 14 дней. Если письма не ушли, в Telegram приходит тревога.
- **`SITE_URL`** должен указывать на реальный домен сайта: от него зависят ссылки в письмах (билет, каталог) и в Telegram. Адрес, куда ЮKassa возвращает покупателя после оплаты (`return_url`), от `SITE_URL` не зависит: виджет берёт адрес страницы, на которой его открыли. Схему и слеш в конце сайт допишет и уберёт сам (`kc.example` → `https://kc.example`).
- **Закрывающий чек.** Включите `RECEIPT_CLOSING` (если бухгалтер подтвердит схему с закрывающим чеком) до первых реальных продаж — если включить позже, ночная задача выбьет закрывающие чеки по всем прошлым проведённым заказам. Ставку НДС (`YOOKASSA_VAT_CODE`) тоже подтверждает бухгалтер.

## Сотрудники

Владелец входит в админку логином и паролем из переменных `ADMIN_LOGIN` и `ADMIN_PASSWORD_HASH`. Остальным владелец (или администратор) заводит личные учётки в разделе «Сотрудники» (`/admin/users`):

- **Администратор** видит и делает всё: заказы, возвраты, экскурсии, новости, вопросы, сотрудники.
- **Гид** видит только сводку ближайших сеансов, списки участников (с печатью и CSV) и отметку прихода по QR-коду.

Смена пароля, роли или отключение входа сразу выкидывают сотрудника из админки на всех устройствах. Себе нельзя сменить роль или отключить вход. Смена пароля владельца в `app.env` на сервере тоже завершает все его сессии.

## Где работает сайт

Всё в России, в Селектеле: персональные данные покупателей записываются и хранятся в базе на российских серверах (152-ФЗ).

| Что | Где |
| --- | --- |
| Сайт | облачный сервер (Ubuntu 24.04), Docker: контейнеры `app` (Next.js), `caddy` (HTTPS, сертификат Let's Encrypt выпускается и продлевается сам), `cron` (ночная и дневная задачи) |
| База данных | PostgreSQL 17 в контейнере `db` на том же сервере, как у сайта гимназии; данные — в томе Docker `kc_db-data`, наружу порт не открыт |
| Копии базы | каждую ночь, restic в приватный контейнер `kc-backups` объектного хранилища Селектела, зашифрованы (раздел «Бэкапы») |
| Обложки | объектное хранилище Селектела (S3), публичный контейнер |
| Письма | SMTP российского почтового сервиса (например, Яндекс 360 для бизнеса) |
| Выкладка | GitHub Actions, `.github/workflows/deploy.yml`: там же собирается образ сайта |

Файлы сервера — в `deploy/`: `compose.yml` (контейнеры), `Caddyfile` (HTTPS и перенаправление `www`), `cron.mjs` (расписание), `deploy.sh` (выкладка), `cloud-init.yml` (первичная настройка сервера), `app.env.example` и `backup.env.example` (шаблоны настроек), `backup.sh` и `restore-db.sh` (копии базы и восстановление), `migrate.mjs` (миграции из образа сайта), `after-deploy.mjs` (обновление страниц после выкладки), `build.env` (адреса, которые попадают в образ), `move-from-vercel.sh` (разовый переезд данных). Образ сайта собирается по `Dockerfile` в GitHub Actions и приходит на сервер готовым: на сервере с 1 ГБ памяти сборка Next не поместилась бы.

На сервере всё лежит в `/home/deploy/app` (`~/app` пользователя `deploy`): `app.env` — настройки и секреты, `backup.env` — настройки копий базы (оба только на сервере), `src/` — код последней выкладки. Полезные команды (в `~/app`):

```bash
docker compose ps
```

```bash
docker compose logs -f --tail 100 app
```

```bash
docker compose up -d app cron backup
```

Первая показывает, что запущено; вторая — журнал сайта (`cron` — журнал задач, `caddy` — HTTPS, `db` — базы, `backup` — копий); третья применяет правку `app.env` без выкладки. Исключения: пароль в `DATABASE_URL` (его базе передаёт выкладка) и `SITE_URL` с `S3_PUBLIC_URL` — они записаны и в образ сайта, поэтому их меняют одновременно в `app.env` и в `deploy/build.env` в репозитории, а затем выкладывают.

## Выкладка

Слияние в `main` само выкладывает сайт. GitHub Actions (`Deploy`) собирает образ сайта — на временной пустой базе, с адресами из `deploy/build.env` — и передаёт его по SSH на сервер вместе с кодом, а там запускает `deploy/deploy.sh`, который:

1. проверяет `app.env` и что адреса в образе совпадают с ним;
2. запускает базу (если она ещё не работает), сверяет её пароль с `DATABASE_URL` и применяет новые миграции из `drizzle/` — из нового образа;
3. перезапускает сайт, расписание, HTTPS и ночные копии базы — посетители несколько секунд ждут ответа, а не видят ошибку; база не перезапускается, если её образ не менялся;
4. ждёт, пока сайт ответит; если не ответил — выкладка помечается упавшей, в её журнале последние строки сайта;
5. обновляет публичные страницы: в образе главная, афиша и карта сайта собраны без экскурсий, поэтому скрипт сбрасывает их кэш (`/api/cron/revalidate`) и заходит на них и на все страницы из карты сайта — первые посетители видят уже настоящие данные.

Выложить `main` вручную: GitHub → Actions → Deploy → Run workflow. Пока секретов сервера нет (раздел «Сервер в Селектеле»), образ всё равно собирается (видно, что сборка не сломана), а выкладка пропускается с пометкой. Миграции применяются до перезапуска, пока работает старая версия сайта, поэтому схема базы меняется только добавлением — старая версия должна продолжать работать с новой схемой.

Сид (начальные данные) на сервере — только для пустой базы: `docker compose run --rm tools npm run db:seed` в `~/app` (образ `tools` при первом запуске соберётся на сервере, это несколько минут).

## Как сменить пароль владельца

1. Сгенерировать хеш (пароль вводится без эха):

   ```bash
   npx tsx scripts/hash-password.ts
   ```

2. На сервере в `~/app/app.env` заменить `ADMIN_PASSWORD_HASH`, **взяв хеш в одинарные кавычки**: `ADMIN_PASSWORD_HASH='$2b$12$...'`. Без них Docker испортит `$` в хеше; `deploy.sh` такую строку не пропустит.
3. Применить: `docker compose up -d app cron` в `~/app`. Все сессии владельца завершатся. Для локальной работы тот же хеш кладётся в `.env.local` с экранированием `\$`.

## Сервер в Селектеле

Первичная настройка — один раз. Понадобятся аккаунт в Селектеле, домен (раздел «Домен») и почтовый ящик для писем (раздел «Почта»). Сервер и хранилище лучше создать в одном регионе (пуле), например в Санкт-Петербурге. Отдельная облачная база не нужна: PostgreSQL работает на самом сервере, как у сайта гимназии.

1. **Ключ для выкладки.** На своём компьютере:

   ```bash
   ssh-keygen -t ed25519 -N "" -C deploy -f deploy_key
   ```

   Получатся `deploy_key` (секретный — только в GitHub) и `deploy_key.pub` (публичный — на сервер).

2. **Облачный сервер.** Панель → Облачная платформа → Серверы → создать в зоне **ru-3b** (Санкт-Петербург): Ubuntu 24.04, линейка Shared, 1 vCPU (доля 20%), 1 ГБ памяти (сайт, база и HTTPS занимают около половины, сборки на сервере нет, `cloud-init.yml` добавляет 2 ГБ подкачки), диск 20 ГБ (тип «Универсальный», 2 000 IOPS — быстрее не нужно), публичный IP-адрес. В поле «Пользовательские данные» (User data) вставить весь `deploy/cloud-init.yml`, заменив строку `ssh-ed25519 ЗАМЕНИТЕ…` на содержимое `deploy_key.pub`. Запомнить публичный IP — дальше он `<IP>`. В ноябре 2026 в зоне ru-9a выдавались адреса из только что полученной Селектелом подсети `136.234.32.0/22`: ping до них проходил, а SSH и сайт — почти ниоткуда. Если до нового сервера не доходит SSH, проверьте `whois -h whois.ripe.net <IP>` (поле `created`) и создайте сервер в другой зоне. Сейчас сайт работает в ru-3b, адрес `136.234.16.49`. Через несколько минут сервер сам поставит Docker и создаст пользователя `deploy`.

3. **Хранилище.** Объектное хранилище → два контейнера: `kc-images` (тип — публичный, обложки) и `kc-backups` (тип — приватный, копии базы). В управлении доступом создать сервисного пользователя с доступом к объектному хранилищу и выпустить ему S3-ключ (Access key и Secret key). Из панели нужны адрес S3 API и регион (например, `https://s3.ru-1.storage.selcloud.ru` и `ru-1`) и публичный адрес контейнера `kc-images` (вида `https://….selstorage.ru`) — его же вписать в `deploy/build.env` в репозитории (слить в `main` до первой выкладки).

4. **Настройки сайта и копий.** Заполнить копии `deploy/app.env.example` (ЮKassa, Telegram и логин владельца — из Vercel → Settings → Environment Variables; `SESSION_SECRET` и `CRON_SECRET` можно сделать новыми; пароль базы в `DATABASE_URL` — новый, `openssl rand -hex 16`) и `deploy/backup.env.example` (S3-ключ и новый `RESTIC_PASSWORD`, `openssl rand -hex 32`; его сразу сохранить в менеджере паролей) и отправить на сервер:

   ```bash
   scp -i deploy_key app.env backup.env deploy@<IP>:app/
   ```

   ```bash
   ssh -i deploy_key deploy@<IP> chmod 600 app/app.env app/backup.env
   ```

   Затем удалить оба файла со своего компьютера: в них все секреты сайта.

5. **Доступ для выкладки.** GitHub → репозиторий → Settings → Secrets and variables → Actions → New repository secret, три секрета: `DEPLOY_HOST` — `<IP>`; `DEPLOY_SSH_KEY` — всё содержимое файла `deploy_key`; `DEPLOY_KNOWN_HOSTS` — вывод команды

   ```bash
   ssh-keyscan -t ed25519 <IP>
   ```

6. **Первая выкладка.** GitHub → Actions → Deploy → Run workflow. Она создаст базу и её схему, запустит сайт и ночные копии. Проверить копии сразу, не дожидаясь ночи: `docker compose run --rm backup now`, затем `docker compose run --rm backup snapshots` (в `~/app`). Если это сервер на замену потерянному — сначала восстановление (раздел «Бэкапы»), копию вручную не делать.

7. Дальше — переезд данных (следующий раздел) и DNS домена (раздел «Домен»).

## Переезд данных с Vercel

Делается один раз, вечером или ночью, когда никто не покупает: заказ, оформленный на старом сайте после копирования, в новую базу не попадёт.

1. Взять строку подключения к старой базе: Vercel → проект `cultural-capital` → Settings → Environment Variables → `DATABASE_URL_UNPOOLED` (адрес без `-pooler`).
2. На сервере:

   ```bash
   ssh -i deploy_key deploy@<IP>
   ```

   ```bash
   bash ~/app/src/deploy/move-from-vercel.sh '<строка из шага 1>'
   ```

   Скрипт одной транзакцией копирует все данные (экскурсии, сеансы, заказы, новости, вопросы, сотрудники; IP-адреса защиты от спама не переносит), переносит обложки из Vercel Blob в хранилище Селектела с заменой адресов в текстах (для этого на сервере один раз соберётся образ `tools`, несколько минут) и перезапускает сайт, обновив страницы уже с данными. Если в новой базе есть заказы, он остановится и ничего не тронет.
3. **Сразу выключить старый сайт:** выложить на Vercel вместо него перенаправление на новый домен. Это уберёт и расписание задач Vercel — иначе старый сайт продолжил бы слать напоминания из старой базы. В пустой папке:

   ```bash
   printf '{"redirects":[{"source":"/(.*)","destination":"https://culturaltours.ru/$1","permanent":true}]}\n' > vercel.json
   ```

   ```bash
   vercel link --yes --project cultural-capital && vercel deploy --prod --yes
   ```

4. **ЮKassa:** в кабинете магазина указать новый адрес сайта и URL уведомлений `https://culturaltours.ru/api/payments/yookassa`. Оплаты, начатые на старом сайте, ночная задача подтянет сама.
5. **Удалить данные за границей**, когда новый сайт проверен: базу в Neon и хранилище Vercel Blob (Vercel → Storage). Проект в Vercel остаётся только с перенаправлением.
6. **Роскомнадзор:** обновить уведомление об обработке персональных данных — база данных теперь в России (Селектел), трансграничной передачи нет (в уведомлениях Telegram нет данных покупателей).
7. **Документы:** в `src/lib/legal.ts` заполнить `processors.mail` (почтовый сервис с юрлицом), сверить название Селектела с договором и поставить в `LEGAL_EDITION` дату переезда.

## Бэкапы

Как у сайта гимназии: каждую ночь в 03:30 по Москве контейнер `backup` снимает копию базы (`pg_dump`) и отправляет её `restic` в приватный контейнер `kc-backups` объектного хранилища Селектела. Хранятся все копии за последние 7 дней, а также 14 ежедневных и 8 еженедельных; всё зашифровано паролем `RESTIC_PASSWORD`, повторяющиеся данные не загружаются заново. Скрипт — `deploy/backup.sh`, настройки — `~/app/backup.env` (образец `deploy/backup.env.example`). Обложки копировать не нужно: они и так лежат в хранилище Селектела.

- **`RESTIC_PASSWORD`** храните и вне сервера (менеджер паролей и владелец): без него копии не прочитать.
- Если копия не получилась, в Telegram приходит тревога (без персональных данных), подробности — `docker compose logs backup`.
- Пока на сервере нет `backup.env`, копии не делаются, а каждая выкладка предупреждает об этом в журнале.

Команды (на сервере, в `~/app`):

```bash
docker compose run --rm backup now
```

```bash
docker compose run --rm backup snapshots
```

Первая делает копию сейчас, вторая показывает список копий.

### Восстановление

```bash
bash ~/app/src/deploy/restore-db.sh latest
```

Вместо `latest` можно указать id копии из списка (`bash ~/app/src/deploy/restore-db.sh` без аргументов). Скрипт покажет время и размер копии, спросит подтверждение, остановит сайт и расписание задач, зальёт копию в базу одной транзакцией (если что-то пойдёт не так, база останется прежней) и запустит всё обратно. Схема базы пересоздаётся из копии; если после копии выходили миграции, следующая выкладка применит их снова. Заказы, оформленные после этой копии, пропадут.

**На новом сервере** (старый потерян): шаги 1–5 раздела «Сервер в Селектеле» с тем же `backup.env` (те же `RESTIC_PASSWORD` и ключи), первая выкладка, затем сразу восстановление — **с id копии из списка, а не `latest`**, и без `backup now` до него: копия ещё пустой базы оказалась бы последней.

## Telegram

С серверов Селектела `api.telegram.org` недоступен — это выяснилось на сервере сайта гимназии 29.10.2026. Поэтому уведомления и тревоги идут через посредника на Vercel, того же, что у сайта гимназии (`svshkola-tg-relay`, папка `relay/` в репозитории `polltov/sv-camp`): он принимает только `sendMessage` и только с ключом. В `app.env`: `TELEGRAM_API_URL=https://svshkola-tg-relay.vercel.app` и `TELEGRAM_RELAY_KEY` — значение `RELAY_KEY` из настроек того проекта в Vercel. Без этих двух строк сайт шлёт прямо в Telegram (так работает и локально).

**Персональные данные.** Telegram — за границей, поэтому в уведомлениях нет имени, телефона и почты покупателя (как у сайта гимназии): номер и сумма заказа, экскурсия, дата, состав группы и ссылка на заказ в админке. Политика и согласие говорят, что трансграничной передачи нет — не добавляйте в уведомления данные покупателя.

## Домен

Адрес сайта — **`culturaltours.ru`**. Домен зарегистрирован в Селектеле 15 ноября 2026 г. на ООО «ИОЦ „Культурная столица“» и оплачен до 15 ноября 2027 г. Автопродление включено: 450 ₽ в год списываются с баланса Селектела, поэтому к ноябрю на балансе должна быть эта сумма сверх оплаты сервера — иначе домен можно потерять. DNS домена — тоже в Селектеле (NS `a.ns.selectel.ru` … `d.ns.selectel.ru`).

1. **Телефон администратора.** Селектел → Домены → `culturaltours.ru` → «Данные администратора» → «Подтвердить» рядом с телефоном, код приходит в СМС. Пока телефон не подтверждён, домен не делегирован и не открывается. Когда Селектел включит обязательную идентификацию администраторов доменов через Госуслуги, её проходит руководитель организации.
2. **DNS** в Селектеле: DNS → Доменные зоны → зона `culturaltours.ru` (создать, если её нет) → две записи `A` с IP сервера — для `culturaltours.ru` и для `www.culturaltours.ru`. Записи начинают работать в течение нескольких часов; когда они дойдут, Caddy на сервере сам получит сертификат HTTPS, а `www` будет перенаправлять на домен без `www`.
3. **`SITE_URL`** в `app.env` — `https://culturaltours.ru` (задаётся до первой выкладки). Письма, Telegram, `sitemap.xml`, `robots.txt` и превью ссылок ведут на этот домен.
4. **Поисковики:** добавить домен в Яндекс Вебмастер и Google Search Console и отправить `https://culturaltours.ru/sitemap.xml`.
5. **Облачные сессии Claude:** открыть `culturaltours.ru` в сетевых настройках среды `cultural-capital`, иначе после выкладки нельзя будет проверить боевой сайт.

## Почта

Письма с билетом, напоминания и «вы не завершили оплату» уходят по SMTP через российский почтовый сервис. Удобнее всего ящик на домене сайта — например, в Яндекс 360 для бизнеса (подойдут и VK WorkSpace, и Unisender Go: у любого из них есть SMTP).

1. Подключить домен к почтовому сервису и добавить в зону `culturaltours.ru` в Селектеле (DNS → Доменные зоны) записи, которые он покажет: `MX` (приём почты), `SPF` и `DKIM` (без них письма попадают в спам).
2. Создать ящик, например `tickets@culturaltours.ru`. Для Яндекса нужен пароль приложения: Яндекс ID → Безопасность → Пароли приложений → Почта.
3. В `app.env`: `SMTP_HOST=smtp.yandex.ru`, `SMTP_PORT=465`, `SMTP_USER` — адрес ящика, `SMTP_PASSWORD` — пароль приложения, `MAIL_FROM=Культурная Столица <тот же адрес>`. Сервис отклоняет письма, если адрес в `MAIL_FROM` не совпадает с ящиком.
4. Проверка: в админке у оплаченного заказа — повторная отправка билета. Если письмо не ушло, причина — в журнале сайта: `docker compose logs app | grep SMTP`.
5. В `src/lib/legal.ts` вписать сервис в `processors.mail` — он появится в политике и согласии.
