# Онлайн-покупка экскурсий — дизайн

Дата: 2026-10-07

## Цель

Клиент заходит на сайт, знакомится с экскурсией и сам покупает билеты удобным способом (карта, СБП, SberPay, T-Pay), без звонков и ручного подтверждения. После оплаты ему приходят билет (от нас) и кассовый чек по 54-ФЗ (от онлайн-кассы ЮKassa).

Сейчас кнопка «Записаться» создаёт заявку без оплаты, админ подтверждает её вручную, а в FAQ обещано «присылаем ссылку на оплату». Этот дизайн заменяет заявки покупкой. Поля `payment_status`/`payment_id` в `orders` уже заложены прошлой спекой (`2026-10-05-admin-panel-design.md`).

Критерии успеха:
- путь «карточка → дата → билеты → оплата» проходится за пару минут, оплата — внутри модалки на сайте;
- после оплаты клиент видит билет на сайте и получает его на почту, чек приходит отдельным письмом от ЮKassa;
- места не перепродаются, в том числе когда двое одновременно покупают последние;
- админ видит оплаченные заказы, отменяет с возвратом денег и переносит на другой сеанс кнопкой, чек возврата формируется автоматически;
- весь путь проверяется в тестовом магазине ЮKassa до подписания договора.

## Решения, принятые с заказчиком

| Вопрос | Решение |
|---|---|
| Юр. форма | ИП или ООО → нужен фискальный чек по 54-ФЗ через онлайн-кассу |
| Платёжный сервис | ЮKassa (сервис Сбера, работает с расчётным счётом в любом банке) + «Чеки от ЮKassa» (облачная касса и ОФД в одном договоре). Модуль изолирован, замена провайдера не затрагивает остальной код |
| Модель покупки | Сразу оплата, без ручного подтверждения. Места держатся за заказом 15 минут, пока клиент платит. Заявки без оплаты больше не создаются |
| Способ оплаты на сайте | Встроенный виджет ЮKassa внутри модалки (`confirmation.type = "embedded"`) |
| Шаги покупки | Экскурсия → дата → количество детских и взрослых билетов → оплата (email, имя, телефон) |
| Проверка на экскурсии | По списку участников сеанса (как сейчас). QR и сканера нет |
| Отмена и возврат | Только админ кнопкой. Сумма подставляется по правилу 24 ч / 50%, редактируется. Деньги и чек возврата — через API ЮKassa |
| Перенос | Админ кнопкой на другой сеанс той же экскурсии, клиенту уходит обновлённый билет |
| Почта | Resend (Vercel Marketplace), отправка с собственного домена проекта |
| Скидки из FAQ | Семейный тариф и −10% за две экскурсии онлайн не применяются; текст FAQ меняется на «для семейного тарифа напишите нам». Промокоды — отдельная задача |

## Вне рамок

QR-коды и сканер билетов, напоминание накануне, письмо «вы не завершили оплату», промокоды и скидки, личный кабинет клиента, частичная отмена части билетов в заказе, несколько возвратов по одному заказу, переезд БД и почты в РФ (152-ФЗ — вместе с отдельной задачей переезда базы).

## Путь клиента

1. **Карточка экскурсии** — как сейчас; кнопка «Записаться» переименовывается в «Купить билет» и открывает модалку для этой экскурсии.
2. **Модалка, шаг «Дата»** — чипы будущих нескрытых сеансов с подписью «свободно N»; без мест — неактивны («мест нет»). Если в карточке уже выбрана дата — она предвыбрана.
3. **Шаг «Билеты»** — счётчики «Детских» / «Взрослых» (сумма ≤ свободных мест, ≤ 20 каждого) и живой итог. Кнопки «Назад» / «Далее».
4. **Шаг «Оплата»** — сводка («Эрмитаж для детей · 12 окт, сб, 11:00 · 2 детских + 1 взрослый · 3 400 ₽»), поля: имя, телефон (маска +7), email (обязательный, подпись «сюда придут билет и чек»), чекбокс «Принимаю условия [оферты](/offer) и согласен на обработку [персональных данных](/privacy)», honeypot. Кнопка «Перейти к оплате · 3 400 ₽».
5. Сервер создаёт заказ «ждёт оплаты» с удержанием мест на 15 минут и платёж в ЮKassa; на месте кнопки появляется **виджет ЮKassa**, поля становятся только для чтения, над виджетом — таймер «Места за вами ещё 14:32» и кнопка «← Изменить» (освобождает места, возвращает к редактируемой форме; новый заказ создаётся при следующем «Перейти к оплате»).
6. Когда таймер доходит до нуля, виджет уничтожается (`checkout.destroy()`), показывается «Время на оплату истекло» и кнопка «Начать заново».
7. После оплаты виджет (или банковское приложение при СБП/SberPay на телефоне) возвращает клиента на `return_url` — **страницу заказа** `/order/<token>`.
8. **Страница заказа** (noindex) по состоянию:
   - ждёт оплаты → «Проверяем оплату…», страница опрашивает статус каждые 3 с до 60 с, затем «Оплата ещё обрабатывается — билет придёт на почту, как только банк подтвердит платёж»;
   - оплачен / проведён → **билет**: фирменный стиль карточки-билета с перфорацией, номер `КС-0057`, экскурсия, дата и время, место встречи, что взять с собой, состав, сумма, имя; кнопка «Распечатать»; строка «Кассовый чек отправлен на email отдельным письмом от ЮKassa»; условия отмены и контакты;
   - не оплачен → «Время на оплату истекло» + ссылка «Выбрать дату заново» (на главную к каталогу);
   - отменён → «Заказ отменён», при возврате — «возврат N ₽ оформлен».
9. **Письмо «Ваш билет КС-0057»** уходит после оплаты (содержимое билета + ссылка на страницу заказа). Кассовый чек присылает ЮKassa.

Индивидуальные экскурсии и семейный тариф — через контакты в FAQ (форма заявки удаляется).

## Архитектура

Стек прежний: Next.js 16 (App Router), Drizzle + стандартный Postgres, Server Actions, Vercel (fra1). Новые модули — каждый с одной задачей и узким интерфейсом:

| Модуль | Назначение |
|---|---|
| `src/server/payments/yookassa.ts` | Тонкий клиент API ЮKassa v3 на `fetch` (Basic auth `shopId:secretKey`, заголовок `Idempotence-Key`): `createPayment`, `getPayment`, `createRefund`, `createReceipt`. Реализует интерфейс `PaymentGateway`; в тестах подменяется подделкой. SDK не используется |
| `src/lib/domain/receipt.ts` | Чистые функции: позиции чека оплаты, возврата и закрывающего чека из заказа (суммы в копейках сходятся с итогом) |
| `src/lib/domain/refund-policy.ts` | Чистая функция суммы возврата по правилу 24 ч / 50% |
| `src/server/checkout.ts` | `startCheckout` (валидация, блокировка сеанса, заказ с удержанием, платёж), `releaseHold` |
| `src/server/payment-sync.ts` | `syncPayment(paymentId)` — единственная точка, меняющая статус заказа по данным ЮKassa; вызывается из webhook, страницы заказа и ночной задачи; идемпотентна |
| `src/server/refunds.ts` | `refundOrder` (отмена с возвратом), `moveOrder` (перенос) |
| `src/server/mail/` | `sendMail({to, subject, html, text})` через Resend REST API + шаблоны писем (билет, отмена, извинение с возвратом). Замена провайдера = замена одного файла |
| `src/app/api/payments/yookassa/route.ts` | Приём уведомлений ЮKassa |
| `src/app/api/cron/nightly/route.ts` | Ночная задача |
| `src/app/(site)/order/[token]/page.tsx` | Страница заказа / билета |
| `src/components/site/CheckoutDialog.tsx` | Модалка-мастер (заменяет `BookingDialog.tsx`), подгружает скрипт виджета `https://yookassa.ru/checkout-widget/v1/checkout-widget.js` только на шаге оплаты |
| `src/components/site/TicketView.tsx` | Билет (страница заказа и печать), использует общий `ticket.css` |

Удаляются: `submitBooking`/`createOrder` (публичное создание заявок), `BookingDialog.tsx`, `bookingSchema` (заменяется `checkoutSchema`).

## Модель данных

Одна миграция Drizzle. Все новые колонки nullable или с default, существующие строки не трогаются.

**tours** — добавить:
- `meeting_point` text not null default `''` — «Место встречи»
- `what_to_bring` text not null default `''` — «Что взять с собой»

**orders** — добавить:
- `access_token` text unique (nullable для старых заявок) — 32 случайных байта в base64url, ключ страницы `/order/<token>`
- `hold_expires_at` timestamptz — до какого момента держатся места заказа «ждёт оплаты»
- `paid_at` timestamptz
- `refunded_amount` integer not null default 0 — рубли
- `refund_id` text
- `ticket_sent_at` timestamptz
- `closing_receipt_at` timestamptz
- `payment_id` — уже есть; добавить уникальный индекс
- `payment_status` — уже есть; хранит последний статус платежа ЮKassa (`pending`, `succeeded`, `canceled`)
- `email` остаётся nullable в схеме (старые заявки), но обязателен в `checkoutSchema`; `comment` остаётся для старых заявок, в новой форме поля нет

**order_status** (enum) — добавить значения `awaiting_payment`, `paid`, `expired`.

**payment_events** — новый журнал:
- `id`, `received_at`, `source` (`webhook` | `sync` | `cron`), `event` (например `payment.succeeded`), `payment_id`, `order_id` (nullable), `payload` jsonb (ответ API ЮKassa целиком), `note` text (что сделано: «paid», «ignored: amount mismatch», …)

## Статусы и переходы

| Статус | Подпись | Занимает места |
|---|---|---|
| `awaiting_payment` | Ждёт оплаты | да, пока `hold_expires_at > now()` |
| `paid` | Оплачен | да |
| `expired` | Не оплачен | нет |
| `done` | Проведён | да |
| `cancelled` | Отменён | нет |
| `new` | Новая (старые заявки) | нет |
| `confirmed` | Подтверждена (старые заявки) | да |

```
awaiting_payment ─(платёж succeeded)──────────────▶ paid ─(экскурсия прошла / админ)─▶ done
awaiting_payment ─(15 мин / «Изменить» / canceled)─▶ expired
expired ─(поздний succeeded, места есть)──────────▶ paid
expired ─(поздний succeeded, мест нет)─────────────▶ cancelled (автовозврат 100%)
paid ─(админ: «Отменить и вернуть»)────────────────▶ cancelled
new → confirmed | cancelled;  confirmed → done | cancelled   (старые заявки, как сейчас)
```

Переходы в `paid` и `expired` выполняет только система (`syncPayment`, `releaseHold`, ночная задача). Админ из интерфейса может: для `paid` — «Отменить и вернуть», «Перенести», «Отметить проведённым»; для старых заявок — прежние кнопки. `canTransition` расширяется этой таблицей; остальные переходы сервер отклоняет.

Перенос не меняет статус — меняется `session_id`.

## Места и удержание

- `seatsTakenSql()` считает участников заказов со статусом `paid`, `done`, `confirmed`, плюс `awaiting_payment` с `hold_expires_at > now()`. Константа `SEAT_HOLDING_STATUSES` обновляется; условие удержания добавляется в SQL.
- `HOLD_MINUTES = 15` — константа в `src/lib/domain/seats.ts`.
- `startCheckout` создаёт заказ в транзакции с `SELECT … FROM tour_sessions WHERE id = $1 FOR UPDATE` — две параллельные покупки последних мест сериализуются, проходит одна. Порядок блокировок «сеанс → заказ», как в существующем `transitionOrder`.
- Перенос блокирует оба сеанса в порядке возрастания `id`.

## Оплата (ЮKassa)

### Начало оплаты — `startCheckout` (Server Action)

1. Валидация `checkoutSchema` (zod, сообщения на русском): `sessionId`, `children`, `adults` (0–20, сумма ≥ 1), `name` (2–80), `phone` (нормализация `+7XXXXXXXXXX`), `email` (обязателен), `consent` (true), `website` (honeypot — молча отклоняется).
2. Лимит: 10 попыток с IP в час (`hitRateLimit("checkout:<ip>", 10, 3600)`), иначе «Слишком много попыток. Попробуйте позже или позвоните нам».
3. Транзакция: блокировка сеанса; сеанс существует, не скрыт, экскурсия опубликована, `starts_at > now()`; свободно ≥ участников (иначе «Осталось мест: N» / «Мест не осталось»). Вставка заказа: `awaiting_payment`, `hold_expires_at = now() + 15 мин`, `access_token`, слепки цен, `total` — **только из цен в БД**, `consent_at = now()`.
4. Вне транзакции: `createPayment` с `Idempotence-Key = order.access_token`:
   - `amount` = `{ value: "3400.00", currency: "RUB" }`, `capture: true`, `confirmation: { type: "embedded" }`;
   - `description` = «КС-0057 · <экскурсия> · 12.10 11:00» (≤ 128 символов);
   - `metadata` = `{ order_id }`;
   - `receipt` = позиции из `receipt.ts` (см. «Чеки») и `customer: { email, phone, full_name }`.
5. Сохранить `payment_id`, `payment_status`; вернуть клиенту `{ confirmationToken, orderToken, holdExpiresAt }`.
6. Если ЮKassa ответила ошибкой или не ответила за 10 с: заказ → `expired` (места освобождаются), клиенту — «Оплата временно недоступна. Попробуйте позже или позвоните нам», в лог — детали.

Виджет инициализируется: `new window.YooMoneyCheckoutWidget({ confirmation_token, return_url: SITE_URL + "/order/" + orderToken, customization: { colors: { control_primary: <терракотовый сайта> } }, error_callback })`, `render("payment-form")`. Токен одноразовый и живёт 1 час; через час ЮKassa сама отменяет неоплаченный платёж.

### `releaseHold(orderToken)` (Server Action)

Кнопка «← Изменить» и «Начать заново»: если заказ `awaiting_payment` — перевести в `expired`. Платёж в ЮKassa не трогаем (неоплаченный платёж отменить через API нельзя; если клиент всё же оплатит — это «поздняя оплата», см. ниже).

### Подтверждение — `syncPayment(paymentId, source)`

Единственная функция, меняющая заказ по данным ЮKassa:

1. `getPayment(paymentId)` — **данным из тела уведомления не доверяем**, берём актуальный объект из API.
2. Найти заказ по `payment_id` (сверить с `metadata.order_id`); не найден → записать в журнал, выйти.
3. Записать событие в `payment_events`.
4. Транзакция, блокировка сеанса, затем заказа:
   - `succeeded`:
     - сумма и валюта не совпадают с `total` → не менять статус, журнал «amount mismatch», алерт в Telegram;
     - заказ `awaiting_payment` → `paid`, `paid_at`;
     - заказ `expired` (поздняя оплата): если места есть → `paid`; если нет → полный возврат (`createRefund`), `cancelled`, `refunded_amount = total`, после транзакции — письмо-извинение и алерт в Telegram;
     - заказ уже `paid`/`done`/`cancelled` → ничего (повтор);
   - `canceled`: `awaiting_payment` → `expired`;
   - `pending`: только обновить `payment_status`.
5. После коммита (через `after()`): при переходе в `paid` — письмо с билетом (`ticket_sent_at` при успехе) и сообщение в Telegram «Оплачен заказ КС-0057 · 3 400 ₽».

### Webhook — `POST /api/payments/yookassa`

- Разобрать JSON, взять `event` и `object.id`. Для `payment.*` → `syncPayment(object.id, "webhook")`; для `refund.succeeded` → записать в журнал (статус заказа к этому моменту уже обновлён синхронно в `refundOrder`).
- Ответ 200 после успешной обработки; при ошибке БД/API — 500, ЮKassa повторяет 24 часа. Некорректное тело — 400.
- Подлинность обеспечивается повторным запросом объекта через API (рекомендация ЮKassa); проверка IP-диапазонов не делается.
- В кабинете ЮKassa подписаться на `payment.succeeded`, `payment.canceled`, `refund.succeeded`.

### Страница заказа как запасной канал

Серверный рендер `/order/[token]`: если заказ `awaiting_payment` и есть `payment_id` — вызвать `syncPayment(…, "sync")` перед отрисовкой. Клиентский компонент вызывает `router.refresh()` каждые 3 с, пока статус «ждёт оплаты» (не дольше 60 с). Так клиент видит билет, даже если webhook задержался.

## Чеки (54-ФЗ)

Через «Чеки от ЮKassa»: ЮKassa регистрирует чек и отправляет его клиенту **на email** (SMS-отправки нет).

- **Чек оплаты** (в запросе платежа): по позиции на тип билета с ненулевым количеством — «Экскурсия «<название>», 12.10.2026 11:00, детский билет» (≤ 128 символов), `quantity`, `amount` = цена за штуку, `vat_code` = `YOOKASSA_VAT_CODE`, `payment_subject: "service"`, `payment_mode: "full_prepayment"` (оплата раньше оказания услуги).
- **Чек возврата** (в запросе возврата): одна позиция «Возврат: Экскурсия «<название>», 12.10.2026 11:00», `quantity: 1`, `amount` = сумма возврата, тот же `vat_code`, `payment_subject: "service"`, `payment_mode: "full_prepayment"`.
- **Закрывающий чек** «Полный расчёт» (ночная задача, если `RECEIPT_CLOSING=on`): `POST /v3/receipts` с `type: "payment"`, `payment_id`, `send: true`, `customer.email`, позициями как в чеке оплаты, но `payment_mode: "full_payment"`, и `settlements: [{ type: "prepayment", amount: total }]`. Только для оплаченных заказов (`paid`/`done`) — отменённые с возвратом сюда не попадают.
- Ставку НДС (`YOOKASSA_VAT_CODE`, по умолчанию `1` — «без НДС») и необходимость закрывающего чека подтверждает бухгалтер; по умолчанию `RECEIPT_CLOSING=off`.

Все суммы в базе — целые рубли; в API передаются строкой с двумя знаками (`"1700.00"`).

## Возврат и перенос (админка)

### «Отменить и вернуть» — `refundOrder(orderId, amount)`

- Доступно для `paid`.
- Сумма по умолчанию — `refundPolicy(total, startsAt, now)`: до начала ≥ 24 ч → `total`; иначе `ceil(total / 2)` (округление в пользу клиента). После начала экскурсии — тоже `ceil(total / 2)`, админ правит вручную.
- Админ может изменить сумму в пределах `0 … total`. `0` — отмена без возврата (API не вызывается).
- `createRefund({ payment_id, amount, receipt })` с `Idempotence-Key = "refund-<orderId>"`. Успех (`succeeded` или `pending`) → заказ `cancelled`, `refunded_amount`, `refund_id`, места освобождаются; клиенту письмо «Заказ КС-0057 отменён, возврат N ₽ — деньги придут в течение нескольких дней в зависимости от банка». Ошибка ЮKassa → сообщение админу с текстом ошибки, заказ не меняется.
- Один возврат на заказ. Дополнительные возвраты при необходимости — в кабинете ЮKassa.

### «Перенести» — `moveOrder(orderId, targetSessionId)`

- Доступно для `paid`. Выбор из будущих нескрытых сеансов **той же экскурсии** со свободными местами ≥ участников заказа.
- Транзакция: блокировка обоих сеансов по возрастанию `id`, проверка мест, `session_id = target`. Цены не пересчитываются, деньги не трогаются.
- Клиенту письмо «Билет КС-0057 перенесён» с новым билетом.

### «Отправить билет повторно»

Для `paid`/`done`: повторная отправка письма с билетом, обновляет `ticket_sent_at`.

## Письма

Resend через интеграцию Vercel Marketplace (`vercel integration add resend` → `RESEND_API_KEY`). Отправитель `MAIL_FROM` (например, `Культурная Столица <tickets@<домен>>`); домен подтверждается DNS-записями Resend (SPF/DKIM).

Шаблоны — простой HTML с инлайн-стилями в цветах сайта + текстовая версия, все данные экранируются:

| Письмо | Когда | Содержимое |
|---|---|---|
| «Ваш билет КС-0057 — <экскурсия>» | оплата | номер, экскурсия, дата/время, место встречи, что взять, состав, сумма, имя, ссылка на `/order/<token>`, «чек придёт отдельным письмом от ЮKassa», условия отмены, контакты |
| «Билет КС-0057 перенесён» | перенос | то же с новой датой |
| «Заказ КС-0057 отменён» | возврат | сумма возврата, сроки зачисления, контакты |
| «Извините, места закончились» | поздняя оплата без мест | полный возврат, ссылка на каталог |

Отправка не блокирует ответ (`after()`), таймаут 10 с. Ошибка → лог; заказ остаётся в своём статусе; в карточке заказа видно «билет не отправлен» (`ticket_sent_at` пуст).

Кнопки по статусу: «Отменить и вернуть» (диалог с суммой), «Перенести» (выбор сеанса), «Отметить проведённым», «Отправить билет повторно». Для старых заявок — прежние кнопки.

- **Форма экскурсии:** поля «Место встречи» и «Что взять с собой» (обычные текстовые).

## Ночная задача

`GET /api/cron/nightly`, расписание в `vercel.ts`: `crons: [{ path: "/api/cron/nightly", schedule: "0 0 * * *" }]` (00:00 UTC = 03:00 МСК). Проверка заголовка `Authorization: Bearer ${CRON_SECRET}`.

1. `awaiting_payment` с истёкшим `hold_expires_at` и `payment_id` → `syncPayment(…, "cron")` (подберёт оплаты, чьи уведомления потерялись); оставшиеся с истёкшим удержанием → `expired`.
2. Заказы `paid` и `done` с `payment_id`, без `closing_receipt_at`, у которых `starts_at < now() − 3 ч` (сюда попадают и заказы, которые админ отметил проведёнными вручную; старые заявки без `payment_id` — нет) → если `RECEIPT_CLOSING=on` — закрывающий чек и `closing_receipt_at`; затем `paid` → `done`. Ошибка по одному заказу логируется и не останавливает остальные (повторится следующей ночью).

## Безопасность

- Сумма платежа считается только на сервере из цен в БД; при подтверждении сверяется с `total`.
- Статус заказа меняется только по данным, полученным из API ЮKassa, а не из тела уведомления.
- `access_token` — 32 случайных байта (crypto), страница заказа `noindex`, токен не попадает в логи и Telegram.
- Ключ ЮKassa и API-ключ Resend — только на сервере (sensitive env в Vercel).
- Лимит попыток оплаты с IP, honeypot.
- Все действия админки (возврат, перенос, повторная отправка) — Server Actions с `requireAdmin()`.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Места кончились, пока клиент заполнял форму | «Осталось мест: N» / «Мест не осталось», возврат на шаг «Билеты» |
| ЮKassa недоступна при создании платежа | заказ `expired`, «Оплата временно недоступна. Попробуйте позже или позвоните нам» |
| Ошибка виджета (`error_callback`) | «Не удалось загрузить форму оплаты» + «Попробовать снова» (`releaseHold` и новый заказ) |
| Время удержания вышло | виджет убирается, «Время на оплату истекло», «Начать заново» |
| Webhook задержался | страница заказа и ночная задача сами опрашивают ЮKassa |
| Поздняя оплата без мест | автовозврат 100%, письмо-извинение, алерт |
| Сумма в платеже не совпала | статус не меняется, алерт в Telegram, разбор вручную |
| Ошибка возврата в ЮKassa | текст ошибки админу, заказ не меняется |
| Письмо не отправилось | лог, «билет не отправлен» в карточке, кнопка повторной отправки |

## Переменные окружения (новые)

| Переменная | Назначение |
|---|---|
| `YOOKASSA_SHOP_ID` | идентификатор магазина (тестового или боевого) |
| `YOOKASSA_SECRET_KEY` | секретный ключ (sensitive) |
| `YOOKASSA_VAT_CODE` | код ставки НДС для чеков, по умолчанию `1` («без НДС») |
| `RECEIPT_CLOSING` | `on` — выбивать закрывающий чек после экскурсии; по умолчанию `off` |
| `RESEND_API_KEY` | ключ Resend (ставится интеграцией Marketplace) |
| `MAIL_FROM` | отправитель писем на домене проекта |
| `CRON_SECRET` | секрет ночной задачи |

`SITE_URL` должен указывать на собственный домен (используется в `return_url` и ссылках в письмах).

## Миграция и запуск

- Миграция только добавляет колонки, значения enum и таблицу; старые заявки (`new`/`confirmed`) остаются и обрабатываются прежними кнопками.
- Работа идёт в отдельной ветке; проверка на превью-деплое с ключами **тестового магазина ЮKassa** (тестовые карты и тестовый СБП). В `main` и на прод — когда есть боевые ключи, домен привязан к Vercel и подтверждён в Resend. До этого на проде остаётся форма заявки.
- Оферта, реквизиты в подвале и обновлённая `/privacy` выкатываются на прод сразу отдельным коммитом — они нужны для одобрения магазина в ЮKassa.

## Тестирование

- **Юнит (Vitest):** `refundPolicy` (≥ 24 ч, < 24 ч, после начала, нечётная сумма); `receipt.ts` (позиции оплаты/возврата/закрывающего чека, сумма позиций = сумме платежа, длина описаний ≤ 128); расширенные `canTransition`; `checkoutSchema`; форматирование суммы для API; шаблоны писем (экранирование, наличие ссылки).
- **Интеграционные (тестовая БД + подделка `PaymentGateway`):**
  - `startCheckout` создаёт заказ с удержанием, места уменьшаются; после истечения удержания — возвращаются;
  - две параллельные покупки последних мест — проходит одна;
  - ошибка ЮKassa при создании платежа → `expired`;
  - `syncPayment`: `succeeded` → `paid`; повтор — без изменений; несовпадение суммы — статус не меняется; `canceled` → `expired`;
  - поздняя оплата: места есть → `paid`; мест нет → автовозврат и `cancelled`;
  - `refundOrder`: сумма, статус, места освободились, повторный вызов не создаёт второй возврат; ошибка API — заказ не меняется;
  - `moveOrder`: успех; нет мест — отказ;
  - ночная задача: истёкшие → `expired`, прошедшие → `done`, закрывающий чек при `RECEIPT_CLOSING=on`;
  - webhook-роут: 200 при успехе, 500 при ошибке, 400 на мусор.
- **В браузере (превью + тестовый магазин):** полный путь тестовой картой и тестовым СБП на десктопе и мобильной ширине; таймер и «Изменить»; страница заказа во всех состояниях; печать билета; письмо пришло; возврат и перенос из админки; чек оплаты и чек возврата видны в кабинете ЮKassa.

## Что сделать владельцу (вне кода)

1. Подать заявку в ЮKassa, подключить «Чеки от ЮKassa», получить `shopId` и секретный ключ; в кабинете указать URL уведомлений `https://<домен>/api/payments/yookassa`.
2. Создать тестовый магазин в ЮKassa (для разработки) и передать его ключи.
3. Назвать домен: привязать его к проекту Vercel и добавить DNS-записи Resend.
4. Дать реквизиты ИП/ООО и текст договора-оферты (и обновлённой политики ПДн).
5. Уточнить у бухгалтера ставку НДС (`YOOKASSA_VAT_CODE`) и нужен ли закрывающий чек (`RECEIPT_CLOSING`), а также формулировку позиции в чеке возврата.
